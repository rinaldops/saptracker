1. Visão Geral do Projeto
1.1 Contexto e Motivação
O SAP GUI Scripting é o mecanismo oficial da SAP para automação de interações com o SAP GUI for Windows. Por anos, a ferramenta de referência para desenvolvimento nessa área foi o Scripting Tracker, criada por Stefan Schnell e distribuída gratuitamente pela comunidade SAP. Em 2024, o autor descontinuou o projeto e encerrou o site de distribuição sem liberar o código-fonte.

Esta especificação define o desenvolvimento de uma ferramenta substituta — denominada SAP GUI Scripting Tool — que não apenas replica as funcionalidades do Scripting Tracker, mas as supera em pontos críticos que o Tracker nunca resolveu: suporte a controles GuiShell/GuiTree, captura de diálogos Win32 nativos e geração de código em múltiplas linguagens de programação.

1.3 Objetivos
Desenvolver uma ferramenta desktop Windows para suporte ao desenvolvimento de scripts SAP GUI Scripting.
Superar as limitações arquiteturais do Scripting Tracker, especialmente em relação a controles GuiShell.
Produzir código de automação limpo em múltiplas linguagens a partir de interações gravadas.
Manter o projeto como software livre e bem documentado para continuidade pela comunidade.
Entregar uma interface visual agradável, organizada por abas, intuitiva para desenvolvedores SAP.

1.4 Escopo
A ferramenta opera exclusivamente em ambientes Windows com SAP GUI for Windows instalado e Scripting habilitado no servidor e cliente. Não há suporte a SAP Web GUI, SAP Fiori ou plataformas não-Windows. O suporte a SAP GUI 64-bit (versão 8.00+) é obrigatório.

2.4 Módulo: shell_handlers
Este módulo é o coração da superioridade da ferramenta em relação ao Scripting Tracker. Cada subclasse de GuiShell recebe um handler dedicado que implementa uma interface comum com três métodos obrigatórios:

Método
Assinatura
Responsabilidade
inspecionar()
inspecionar(obj) -> dict
Retorna estrutura com todo o conteúdo interno do controle para exibição no Analyser.
tirar_snapshot()
tirar_snapshot(obj) -> dict
Captura o estado atual do controle para o sistema de diff do Recorder.
gerar_codigo()
gerar_codigo(id, antes, depois, lang) -> list[str]
Compara dois snapshots e retorna as linhas de código correspondentes às mudanças.

3.3 Critérios de Aceite por Fase
Fase 2 — Analyser Base
Ao conectar ao SAP GUI ativo, a árvore de objetos é populada em menos de 3 segundos.
Cada nó da árvore exibe: ID completo, tipo, texto e posição (top, left, width, height).
Clicar com botão direito em qualquer nó aciona o Visualize (moldura vermelha) no SAP.
Botão "Copiar ID" copia o ID completo para o clipboard.

Fase 3 — Shell Handlers
Ao encontrar um GuiGridView na árvore, o painel de detalhes exibe todas as colunas e os valores das células visíveis.
Ao encontrar um GuiTree, o painel exibe a hierarquia completa de nós com chaves e textos.
Ao encontrar um GuiTextEdit, o painel exibe o número de linhas e o conteúdo atual.
Ao encontrar um GuiCalendar, o painel exibe a data de foco e o intervalo de seleção.

Fase 5 — Recorder Polling
Ao clicar em um nó do GuiTree durante a gravação, o código correspondente (SelectNode) é inserido no script.
Ao selecionar células num GuiGridView, o código de SetCurrentCell/SelectedRows é gerado.
A granularidade do polling é configurável (padrão: 200ms). Não deve consumir mais de 3% de CPU.

Fase 6 — Recorder Win32
Quando uma janela Win32 nativa aparece durante a gravação, um bloco de código AutoItX é inserido automaticamente no script com o título e a classe da janela detectada.
Para diálogos de arquivo padrão (CLASS:#32770), o código gerado inclui o preenchimento do campo de nome de arquivo e o clique no botão de confirmação, com placeholders para os valores.

4.3 Tratamento de Erros COM
Toda chamada ao SAP GUI COM pode falhar se a sessão for fechada, a tela mudar ou o objeto não existir mais. O padrão obrigatório é:

import pywintypes
from src.utils.logger import get_logger

logger = get_logger(__name__)

def _chamar_com_seguro(func: Callable, *args, default=None) -> Any:
    """Executa uma chamada COM com tratamento de erro padronizado.

    Retorna default se a chamada falhar por qualquer razão COM.
    Erros são logados em DEBUG para não poluir a interface.
    """
    try:
        return func(*args)
    except pywintypes.com_error as e:
        logger.debug("Chamada COM falhou: %s | args: %s", e, args)
        return default
    except AttributeError as e:
        logger.debug("Atributo COM indisponível: %s", e)
        return default

4.4 Threading — Regras Obrigatórias

⚠️  Regra Crítica — Thread Safety com PyQt6 e COM
Toda atualização de widget PyQt6 DEVE ocorrer na thread principal. Threads de background (polling, win32gui) NUNCA devem modificar widgets diretamente. Use sempre signals/slots para comunicação entre threads. Além disso, objetos COM do SAP GUI não são thread-safe: cada thread que usa COM deve chamar pythoncom.CoInitialize() no início e pythoncom.CoUninitialize() no final.

# PADRÃO OBRIGATÓRIO para threads de background

import pythoncom
from PyQt6.QtCore import QThread, pyqtSignal

class PollingWorker(QThread):
    """Thread de polling para detecção de mudanças em GuiShell."""

    mudanca_detectada = pyqtSignal(str, dict)  # (obj_id, codigo_gerado)

    def run(self) -> None:
        pythoncom.CoInitialize()  # OBRIGATÓRIO em threads COM
        try:
            self._loop_polling()
        finally:
            pythoncom.CoUninitialize()  # SEMPRE limpar

    def _loop_polling(self) -> None:
        while not self.isInterruptionRequested():
            snap = self._tirar_snapshot()
            mudancas = self._detectar_mudancas(snap)
            if mudancas:
                self.mudanca_detectada.emit(...)  # ← signal, não UI direta
            self.msleep(POLLING_INTERVAL_MS)

5. Sistema de Geração de Código
5.1 Arquitetura do Codegen
O sistema de geração de código é baseado em uma classe abstrata CodeGenerator com templates Jinja2 por linguagem. Essa separação garante que adicionar suporte a uma nova linguagem exija apenas a criação de um novo arquivo de generator e seus templates, sem modificar nenhum código existente.

# src/codegen/base.py

from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class Acao:
    """Representa uma ação SAP capturada pelo Recorder."""
    tipo: str          # "set_text", "press", "select_node", etc.
    obj_id: str        # ID completo do objeto SAP
    args: dict         # Argumentos específicos da ação
    origem: str        # "com_event" | "polling" | "win32"

class CodeGenerator(ABC):
    """Interface base para todos os geradores de código."""

    @abstractmethod
    def gerar_cabecalho(self, info_sessao: dict) -> str:
        """Gera o cabeçalho do script (imports, conexão SAP)."""
        ...

    @abstractmethod
    def gerar_linha(self, acao: Acao) -> str:
        """Converte uma Acao em uma linha de código."""
        ...

    @abstractmethod
    def gerar_rodape(self) -> str:
        """Gera o rodapé do script (fechamento de recursos)."""
        ...

    def gerar_script_completo(self, acoes: list[Acao], info: dict) -> str:
        """Combina cabeçalho + linhas + rodapé em um script completo."""
        partes = [self.gerar_cabecalho(info)]
        partes += [self.gerar_linha(a) for a in acoes]
        partes.append(self.gerar_rodape())
        return "\n".join(partes)

6. Interface Visual
6.1 Princípios de Design
Clareza: cada aba tem um propósito único e bem definido. Sem mistura de funcionalidades.
Consistência: paleta de cores, tipografia e espaçamentos uniformes em toda a aplicação.
Contexto: o painel de detalhes sempre mostra informações relevantes ao item selecionado.
Eficiência: as ações mais frequentes (copiar ID, atualizar árvore, iniciar/parar gravação) estão a um clique.
Feedback visual: estados da ferramenta (conectado, gravando, parado) são sempre visíveis na status bar.

8.2 Mocking do SAP GUI COM
Testes de handlers e geradores não devem depender de um SAP GUI real. Use unittest.mock para simular objetos COM:

# tests/unit/test_grid_view_handler.py
from unittest.mock import MagicMock, patch
from src.core.shell_handlers.grid_view import GuiGridViewHandler

def _mock_grid(colunas: list[str], linhas: list[dict]) -> MagicMock:
    """Cria um mock de GuiGridView com dados de teste."""
    grid = MagicMock()
    col_mock = MagicMock()
    col_mock.Length = len(colunas)
    col_mock.ElementAt.side_effect = lambda i: colunas[i]
    grid.GetColumnNames.return_value = col_mock
    grid.RowCount = len(linhas)
    grid.GetCellValue.side_effect = lambda row, col: linhas[row].get(col, "")
    grid.CurrentCellRow = 0
    grid.CurrentCellColumn = colunas[0] if colunas else ""
    grid.SelectedRows = ""
    grid.FirstVisibleRow = 0
    return grid

def test_inspecionar_retorna_colunas_e_linhas():
    handler = GuiGridViewHandler()
    mock = _mock_grid(
        colunas=["Material", "Qtd", "Valor"],
        linhas=[{"Material": "MAT001", "Qtd": "10", "Valor": "500"}],
    )
    resultado = handler.inspecionar(mock)
    assert resultado["colunas"] == ["Material", "Qtd", "Valor"]
    assert resultado["linhas"][0]["Material"] == "MAT001"
    assert resultado["total"] == 1

10. Guia de Contribuição
10.1 Como Adicionar um Novo Handler GuiShell
Para adicionar suporte a um novo tipo de GuiShell (ex: GuiOfficeIntegration), siga estes passos:

Crie o arquivo src/core/shell_handlers/office_integration.py.
Implemente a classe GuiOfficeIntegrationHandler herdando de GuiShellHandler.
Implemente os três métodos obrigatórios: inspecionar(), tirar_snapshot() e gerar_codigo().
Registre o handler em src/core/shell_handlers/__init__.py adicionando ao dicionário HANDLERS.
Escreva testes unitários em tests/unit/test_office_integration_handler.py usando mocks COM.
Atualize docs/shell_handlers.rst com a documentação do novo handler.
Abra um Pull Request descrevendo quais propriedades/métodos do tipo SAP foram mapeados.

10.2 Como Adicionar uma Nova Linguagem de Geração
Crie src/codegen/nova_linguagem_gen.py herdando de CodeGenerator.
Crie os templates Jinja2 em src/codegen/templates/nova_linguagem/.
Registre a linguagem no dicionário GENERATORS em src/codegen/__init__.py.
Adicione a linguagem ao ComboBox de seleção em src/ui/tab_recorder.py.
Escreva testes para cada tipo de ação (set_text, press, select_node, etc.).

10.3 Fluxo de Pull Request
Todo PR deve ter: descrição do problema, solução adotada, testes adicionados.
O CI (GitHub Actions) deve passar: ruff (lint), mypy (tipos), pytest (testes).
Cobertura de testes não pode cair abaixo do piso atual.
Toda nova funcionalidade deve ter docstrings e entrada no CHANGELOG.md.
